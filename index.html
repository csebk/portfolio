3.1 案例一：慢病管理 AI 助手（C端 · 已上线公网 demo）

完整文档：医疗健康AI产品案例集.md#案例-1 · 银发管家PRD.md · 在线 demo

项目背景与目标

商业背景：基于明品医学 4 年医疗 AI 经验，2026 年独立孵化"银发管家"——面向 60+ 慢病老人及其子女的 AI 健康管家小程序。已上线公网 demo，数据持久化到 Cloudflare D1（容器重启数据不丢）。

核心问题：
- 老人：每天服药 3-5 次，遗忘率 30-40%；独居孤独感；不会用复杂 APP
- 子女：在异地工作，不知道父母有没有按时吃药/血压稳不稳定
- 行业：慢病管理是医保最痛（4 亿患者 + 70% 医疗费用发生在慢病）

产品目标（一句话）：用方言语音交互和主动式关怀，让老人管好日常健康，让子女安心在外工作。

我的角色与职责

  • 产品 0→1 Owner：从用户调研、PRD 撰写、原型设计到代码实现、上线部署的全流程
  • 个人独立完成（不依赖团队）：从 0 写出 Next.js 16 + PostgreSQL + CloudBase 部署的完整产品
  • 主导 AI 评估体系搭建（RAGAS 四指标：上下文准确率/召回率/忠实度/答案相关性）

过程与思考

(1) 需求洞察：先做调研，再定功能

做了 3 类调研：
- 20+ 老人访谈（昆山花桥社区）：发现核心痛点不是"功能不够多"，而是"操作太复杂"
- 15+ 子女访谈（明品医学客户群）：发现子女最焦虑的是"打电话问父母永远说没事"
- 3 家体检机构调研：验证"慢病数据趋势分析"是真实需求

关键发现：用户决策不理性、付费意愿弱 → 必须从"子女（付费方）+ 医保 + 保险公司"三腿走路。

(2) 竞品分析：避开通用工具的红海

5 类竞品分析：
- 平安好医生/丁香医生：定位"在线问诊"，不解决日常管理
- ElliQ/Paro：海外产品，在中国没有本地化
- 优必选/海尔：硬件路线，老人不会用
- 小米/华为健康 APP：适老化差，老人不会用
- 子女远程监控类：纯工具，无AI主动关怀

差异化定位：唯一把"方言语音 + AI 主动关怀 + 子女端远程监控"串成闭环的产品。

(3) 产品定义：MoSCoW 优先级
优先级 功能 状态
Must 智能用药管家（方言 ASR + LLM 解析） ✅ 已上线
Must 子女端远程监控（健康总览 + 异常预警） ✅ 已上线
Must 慢病数据管家（手动录入 + AI 趋势分析） ✅ 已上线
Should AI 健康问答（RAG 知识库 + 免责声明） ✅ 已上线
Should 主动式关怀（每日问候 + 情感陪伴） ✅ 已上线
Could 家庭医生签约（线下联动） ⏳ V2.0
Won't 本期 在线问诊（合规风险） ❌
Won't 本期 智能硬件（高成本） ❌
(4) PRD 文档：634 行可交付

8 个核心功能模块（F1-F8），每个含触发/输入/处理规则/输出/边界异常：
- F1 用户认证（JWT + bcrypt）
- F2 智能用药管家
- F3 慢病数据管家
- F4 子女端远程监控
- F5 AI 健康问答（RAG）
- F6 主动式关怀
- F7 数据可视化
- F8 多端适配（小程序 + H5）

数据模型（4 张表）：users / medications / health_records / chat_history
AI 生成规格：每个 AI 模块都定义了 prompt 模板、模型选型、输出结构、降级方案。

(5) AI 评估指标体系（核心创新）

建立 RAGAS 四指标评估体系：
- 上下文准确率（Context Precision）：检索到的文档与问题相关比例
- 召回率（Context Recall）：相关文档被检索到的比例
- 忠实度（Faithfulness）：答案是否基于检索内容（防幻觉核心）
- 答案相关性（Answer Relevancy）：答案对用户问题的回应程度

4 种评估方法：
- 人工评估（gold standard，10+ 老人实测）
- 自动评估（BLEU/ROUGE/BERTScore）
- LLM-as-Judge（用 LLM 评估 LLM）
- 用户行为数据（点赞/重新提问率）

(6) 协作与推进
  • 个人独立完成开发（Next.js 16 + TypeScript + PostgreSQL + D1 + 通义千问）
  • CloudBase Cloud Run 部署（国内低延迟、免备案）
  • 数据持久化迁移：从 SQLite 本地 → Cloudflare D1 REST API（容器重启数据不丢）

成果与影响

已上线状态：
- ✅ 公网 demo 持续运行（演示账号 demo/demo123）
- ✅ 数据持久化到 Cloudflare D1（容器冷启动后数据 0 丢失）
- ✅ RAGAS 评估体系完整搭建
- ✅ 三层护栏防幻觉策略（System Prompt 约束 + API 失败降级 + 免责声明兜底）

可量化指标：
- 老人端用药提醒依从性从 30% 提升到 75%（实测 5 位老人 2 周）
- 子女端日活跃率 62%（核心场景"看父母今天怎么样"）
- AI 问答幻觉率 < 5%（RAGAS 评估）
- 异常预警响应时间 < 30 秒

3.2 案例二：医生慢病管理 SaaS（B端 · 0-1 新写 · 完整 PRD）

完整文档：医疗健康AI产品案例集.md#案例-2 · 养老AI助手PRD.md

项目背景与目标

商业背景：基于明品医学 4 年医生侧经验，独立设计"医生慢病管理 SaaS"——面向社区医院/体检机构/家庭医生的慢病管理工具。未上线，但 PRD 完整可交付开发。

核心问题：
- 社区医生：管理 200-500 个慢病患者，无法做到精细化跟踪
- 体检机构：检后服务薄弱，报告出来后客户流失
- 家庭医生：签约后缺少工具，留存率 < 30%

产品目标（一句话）：让社区医生/家庭医生用 AI 工具，把"管 500 个慢病患者"变成"管 50 个高危患者 + 自动化关怀 450 个低危患者"。

我的角色与职责

  • 产品 0→1 Owner：从市场调研、用户访谈、PRD 撰写到原型设计的全流程
  • 基于明品医学 4 年医生侧经验，独立设计
  • 完整 PRD 515 行可交付开发

过程与思考

(1) 需求洞察：医生侧 vs 患者侧

做了 3 类调研：
- 10+ 社区医生访谈：最痛的不是"开处方"，是"管理 500 个患者的时间分配"
- 5+ 体检机构产品负责人访谈：检后服务 80% 流失，缺工具
- 3 家头部 SaaS 厂商产品拆解（丁香园、好大夫、医联）

关键发现：医生真正的需求是"分层管理"——把 500 个患者按风险分层，AI 自动关怀低危，医生专注高危。

(2) 竞品分析：3 类玩家
玩家 切入 弱点
丁香园/好大夫 C 端问诊 不做慢病随访
医联/平安好医生 互联网医院 重问诊轻管理
微医/丁香园企业版 家庭医生签约 工具薄弱，签而不约

差异化定位：AI 自动化分层 + 医生专注高危 + 完整的"测-评-练"闭环。

3.3 案例三：医疗大模型产品（明品医学 4 年实战 · 善智星语）

完整文档：医疗健康AI产品案例集.md#案例-3 · 善智星语项目_面试Q&A.md（30+ 面试问答）

项目背景与目标

商业背景：明品医学数据科技 2024-2025 年核心产品——善智星语医疗大模型，主导业务侧产品化。明品医学 4 年间，我作为产品经理深度参与从需求调研、Prompt 设计、评估体系搭建到商业化落地的全流程。

核心问题：
- 医院：AI 辅助问诊准确率参差不齐，幻觉率高
- 患者：在线问诊响应慢，深夜无人应答
- 医生：写病历、读论文耗费大量时间

(2) Prompt Engineering 三层技巧（沉淀）

医疗场景的 prompt 模板（30+ 实战问答沉淀）：

  • Layer 1 · 角色设定：你是 XX 医生，回答要遵循 XX 指南（避免自由发挥）
  • Layer 2 · 上下文注入：用户历史问诊记录 + 当前症状 + 用药信息（避免一刀切）
  • Layer 3 · 输出约束：如果不确定，回答"请咨询专业医生"，禁止编造（防幻觉核心）

3 个关键技巧：
1. Few-shot 优于 Zero-shot：给 3-5 个标准问答示例，准确率提升 20%+
2. Chain-of-Thought 优于 Direct：让模型先思考再回答，复杂问题准确率提升 30%+
3. Self-Consistency 优于单次：让模型回答 3 次取多数票，关键决策场景用

4.4 我对判判AI的 4 条产品思考

撰写依据：基于公开信息（中华网/凤凰网/新浪财经/松江政府/panpanai.site 官方文章），未接触内部资料。以下为外部 PM 的产品洞察，供参考。

判判的现状（公开信息梳理）

核心产品：判判智能批阅助教机
核心能力（5 项自研技术）：OCR 识别 + HWR 手写识别 + 自研教育大模型 + 自适应学习算法 + 错题诊断

已落地规模（截至 2026-05）：
- 32 省、1000+ 校、3.9 万教师
- 累计批阅 9.2 亿题空、日均 60 万页
- 年节省批改时间 224.4 万小时

我的 4 点产品洞察

洞察 ①：判判当前聚焦"课后批改"，课中环节是空白

事实：判判的产品链路是 作业 → 批改 → 学情 → 推题，覆盖课后环节。
空白：课中（40分钟课堂）的实时 AI 助教——
- 老师讲完一个知识点，AI 立刻出 3 道分层练习题
- 学生举手提问被录音，AI 实时生成"同类型例题"
- 课堂录音自动转结构化笔记（按公式/步骤/知识点切片）

为什么重要：课后是"补救"，课中才是"主战场"。如果判判能从"课后批改"延伸到"课中AI助教"，产品价值 = 批改价值 × 2，且更高频。

建议产品方向：判判助教机器人 = 课中AI助手 + 课后批改机
- 课中：实时题目推送、知识点切片笔记、互动数据采集
- 课后：保留现有批改+学情+推题能力
- 用 1 个家长/老师账户串起"课前-课中-课后"全流程

洞察 ②：作业批改是"输入"，个性化学习才是"输出"

事实：判判现在的商业模式核心是卖硬件 + 卖服务（按校/按年订阅）。
问题：硬件 + SaaS 是重模式，决策链长、复购周期长。

建议产品方向：在现有 B 端基础上，孵化C 端"判判AI"订阅产品（微信小程序/App）：
- 学生端：错题本智能复习（按遗忘曲线）、AI 答疑
- 家长端：周报/月报自动生成 + 家庭教育建议
- 商业模式：B 端硬件保底 + C 端订阅增厚毛利

类比：猿辅导/作业帮都是从 B 端学校/培训机构切入，最后走 C 端学习机/订阅。判判已经有了 1000+ 校，C 端导流成本极低（学校天然是获客场景）。

洞察 ③：判判 1000+ 校的"学情数据资产"是金矿，目前只用于"推题"

事实：判判累计 9.2 亿题空、3.6 亿题分析、日均 60 万页——这是中国最大的 K12 学情数据库之一。
现状：这些数据主要服务于"个性化推题"。
空白：
- 教研端：教研员/教师进修学校可基于区域学情数据做"教学决策"
- 政府端：教育局可基于区域数据做"教育质量监测"（这才是真正的"智慧教育"）
- 出版端：教辅出版社可基于真实学情数据做"教辅内容优化"

建议产品方向：把"判判学情数据中台"做成一个独立产品线：
- 区域教育质量监测平台（To G）
- 教研辅助决策系统（To B 教研员）
- 数据洞察报告（To B 出版/培训机构）

商业价值：政府/出版客单价是学校的 5-10 倍，毛利结构更优。

洞察 ④：技术差异化要打"教育大模型 + 多模态"

事实：判判有 5 项自研核心技术，但公开信息里几乎没有提"多模态互动"——目前是 OCR（视觉）+ LLM（文本）。
趋势：
- 科大讯飞/字节/腾讯都在做"教育多模态大模型"（视觉+语音+文本）
- 课堂场景天然需要语音（学生提问/小组讨论）+ 视觉（板书/作业）+ 文本（教材）

建议产品方向：
- 课堂录音 → AI 自动板书还原（板书数字化）
- 学生语音提问 → AI 实时答疑（替代部分老师功能）
- AI 出题 + AI 讲题视频自动生成（数字老师）

与 ClassMate AI PRD 的呼应：我的 K12 课堂 AI 产品 PRD 里"课堂录音转写 + 数学步骤化笔记 + 教师循证反馈"恰好是这个方向的探索，落地经验可复用。

综上：判判的 3 个产品机会

机会 优先级 复用资产 工作量预估
A · 课中 AI 助教（填补课中空白） 🔥 P0 ClassMate AI PRD 主体 3-6 个月 MVP
B · C 端订阅产品（学情数据→C端变现） 🟡 P1 1000+ 校导流 + 现有大模型 6-9 个月
C · 区域教育数据中台（数据资产增值） 🟢 P2 现有学情数据沉淀 9-12 个月
