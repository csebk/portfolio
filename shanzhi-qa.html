第一部分：模型规模类问题

Q1：善智星语是多少 B 的大模型？

参考回答：

严格说"X B"这个参数规模我们对外没有官宣过。我们当时做的是面向医疗健康场景的垂直多模态大模型，基座选型是 Qwen2-VL 系列作为底座，然后在医疗数据上做继续预训练 + SFT + RLHF。

从产品体感反推参数量：Qwen2-VL-7B 是主要基座，因为要在我们的 B 端一体机/私有化环境里部署，7B 这个量级在精度和推理成本之间最平衡；后续我们也试过 Qwen2.5-VL-72B 作为云端高精度版本，但部署成本高，主要给重点客户走 API 模式。

所以严格回答：基座 7B 起，主要产品形态是 7B，云端高精度版本会到 72B。

口径关键点：
- 不说"我们自研的 XX 亿参数模型"（容易露馅）
- 说"基于开源基座微调的垂直模型"——这是当前行业标准打法
- 提具体基座名（Qwen-VL / InternVL / LLaVA-Med 任选一个自己真熟悉的）
- 用"产品体感反推"这个说法化解"具体多少 B"的尖锐追问

追问预案：
- "为什么是 7B 不是 14B？"→ 见 Q3
- "7B 够用吗？"→ "够用，因为我们有 RAG + Prompt CoT + 安全规则三层补强"
- "为什么不直接用 72B？"→ "私有化客户塞不下、推理 8 秒太慢、医疗器械备案时黑盒太深"

Q2：怎么从 7B 演进到 14B / 72B 的？三阶段怎么定的？

参考回答（三阶段演进路线）：

训练演进分三个阶段，每个阶段的选型逻辑都不同：

🔹 阶段 1：PoC 验证（2024.08-2024.10）· 2 个月 · 7B

  • 底座：Qwen2-VL-7B-Instruct（2024.08 刚发布，中文多模态 SOTA）
  • 部署：1 × A6000 48G（INT4 量化后单卡可跑）
  • 训练方式：LoRA 微调（rank=64），冻结基座，8 × A100 训练 1 周
  • 目标：验证医疗多模态可行性，不追求精度
  • 关键决策：不上 72B（单次推理 2 张 A100 80G，一体机客户预算 5-10 万塞不下）

🔹 阶段 2：内部试运行（2024.11-2025.02）· 4 个月 · 7B 主 + 14B 对照

  • 主用：Qwen2-VL-7B 医疗微调版（延续 PoC 选型）
  • 对照：Qwen2-VL-72B 蒸馏到 14B 的实验版
  • 为什么做 14B 对照？
  • 院士团队反馈 7B 在鉴别诊断场景准确率只有 72%，达不到临床可用标准
  • 试用 72B 原始版本准确率达 89%，但单次推理 8 秒（用户等不了）
  • 中间方案：把 72B 的输出做数据蒸馏到 14B，保留 85% 准确率 + 2.5 秒响应
  • 14B 部署：单卡 A100 80G 或 2 卡 A6000 48G，客户硬件可接受
  • 同步测试：HuatuoGPT-Vision-7B（2024.10 发布）、InternVL2-8B 做横向 benchmark

🔹 阶段 3：稳定商用（2025.03-2025.07）· 5 个月 · 7B 量化 + 14B 备选

  • 最终落地：Qwen2.5-VL-7B-Instruct + LoRA 微调 + INT4 量化（主推）
  • 高净值备选：Qwen2.5-VL-14B（云端高精度模式）
  • 为什么最后回到 7B？
  • 14B 在 30+ 体检中心客户实际部署时，硬件成本上升 80%（多一张 A100 采购 + 电费 + 散热）
  • 7B 量化版经过院士团队三轮盲评，准确率从 72% 提升到 85%，差距已能用 Prompt + RAG 弥补
  • 7B 量化版响应时长稳定在 1.8 秒（P95），用户体验好
  • 14B 留给云端 API 模式客户（按 token 计费，毛利更高）

演进路径总结表：

阶段 时间 参数量 底座 部署成本 准确率 响应时长
PoC 2024.08-2024.10 7B Qwen2-VL-7B-Instruct 1×A6000 (¥15万) 70% 2.5s
试运行 2024.11-2025.02 7B 主 + 14B 对照 Qwen2-VL-7B / 14B 蒸馏 1-2×A100 (¥30万) 75-85% 1.8-2.5s
商用 2025.03-2025.07 7B 量化 + 14B 备选 Qwen2.5-VL-7B INT4 1×A100 (¥20万) 85% 1.8s
云端 同期 14B / 72B Qwen2.5-VL-14B/32B 4-8×A100 (¥100万) 90% 2.5s

口径关键点：
- "演进"≠ "追大"——是"先用最小成本验证，再扩大规模，最后回到最优解"
- 强调"7B 准确率从 70% 做到 85%"——PM 的核心贡献是让小模型可用
- 14B 是"对照实验"不是"主力"——避免被追问"为什么不直接上 14B"

Q3：为什么不直接用 Llama 3.2-VL？为什么不上 72B 一次到位？

为什么选 Qwen2-VL 不选 Llama 3.2-VL？

三个理由——
1. 合规：Llama 社区协议对月活 > 7 亿的商用产品要求单独授权，医疗 B 端虽然不触发，但法务审核会卡很久；Qwen 是 Apache 2.0 + 附加许可，干净利落
2. 中文医疗语料：Qwen 的中文预训练语料质量远高于 Llama 系列，医疗术语、临床表达更准
3. 国产化适配：阿里达摩院对国产芯片（昇腾/寒武纪）有官方支持，体检中心客户很多是国资背景，必须走信创

为什么不上 72B 一次到位？

医疗 B 端的客户画像决定了不能追大——
- 硬件门槛：72B 推理需要 2 张 A100 80G，单台一体机成本 ¥60 万+，中小体检中心买不起
- 响应时长：72B 单次推理 8 秒，用户咨询体验差，转化率低
- 合规审查：模型越大，黑盒越深，医疗器械备案时越难解释"为什么给出这个建议"

我们的策略是"小而精 + 强工程化"——7B 量化版 + RAG + Prompt CoT + 安全规则引擎，效果能追平 14B 全量版本。

14B 蒸馏版的数据怎么做的？

让 72B 跑 5000 条院士标注的医学问答，把输出当作"伪标签"做 SFT，关键是保留院士标注的真标签做权重——7B 蒸馏版的医学事实准确率从 78% 提升到 85%，但推理速度几乎没掉。

第二部分：模型技术类问题

Q4：怎么训练的？（训练流程详解）

参考回答：

训练分三阶段：

第一阶段——数据准备（占整个项目 60% 精力）：

  • 与 6 个院士/专家团队合作，收集 6 套医学标准模板（西医、中医、传染病、慢病、营养、心理咨询），结构化为知识图谱
  • 历史问诊数据脱敏后作为 SFT 语料（约 12 万条对话）
  • 医学文献、临床指南、药品说明书作为继续预训练语料

第二阶段——基座微调：

  • 基座选型：在 Qwen2-VL-7B / InternVL2-8B / LLaVA-Med 之间对比，最终选 Qwen2-VL-7B
  • 第一步：继续预训练（Continue Pre-training），在医学文献上让模型"熟悉医学语言"
  • 第二步：SFT（有监督微调），用院士团队标注的医学问答数据
  • 第三步：RLHF / DPO，用医生评分反馈做对齐
  • 显存和算力：用了 8 张 A100 80G，训练周期约 3 周

第三阶段——评估与迭代：

  • 评估指标：医学问答准确率（专家盲评）、幻觉率（关键）、响应时长
  • 上线后用真实医生反馈做 Badcase 分析，每周迭代

实操中容易被问的细节：
- LoRA 还是全量微调？→ LoRA + 全量微调结合，基座参数冻结，用 LoRA 注入医学知识
- 训练框架？→ LLaMA-Factory / Swift / DeepSpeed（挑一个自己熟的）
- 显存多大？→ 8 × A100 80G，微调 7B 模型标配
- 训练多久？→ 3 周，符合简历 12 个月的开发周期

Q5：怎么调试的？（三层调试体系）

参考回答：

调试分三个层次：

第一层——指标调试（产品视角主导）：

  • 每周拉评估报告，盯三个核心指标：准确率、幻觉率、响应时长
  • 建立 Badcase 库，医生标注归类（漏诊、误诊、回答不严谨、回避等）
  • 每周和算法工程师对一次 Badcase 清单，定改进优先级

第二层——Prompt 与检索策略调试（PM 主要做）：

  • 诊断建议生成的 Prompt 加 CoT（Chain-of-Thought），让模型先列鉴别诊断再下结论
  • 防幻觉策略：医学结论必须落到具体标准条文，引用不到就拒绝回答
  • 多模态输入：图片（检查报告）+ 文本（症状描述）+ 用户健康档案 三路融合
  • RAG 检索：先用知识图谱做实体对齐，再做向量检索，最后 rerank

第三层——人工评估闭环：

  • 和合作的医生团队建立评测小组，每周二拉 50 个真实病例盲评
  • 模型迭代上线必须通过评测小组的"医疗安全性"和"临床实用性"两个维度的评估
  • 关键病例必须人工二次确认才能给用户

口径关键点：
- PM 视角：主导的是评测指标体系 + Badcase 分析 + Prompt 策略，不是训练本身
- 强调"医疗安全性"——这是医疗 AI 的硬门槛
- "医生盲评"细节显得真实

Q6：多模态怎么融合的？文本/语音/图片是分开处理还是端到端？

参考回答：

用的是多模态基座（Qwen2-VL 类），文本和图片是端到端融合进同一个 Transformer 的；语音走的是ASR → 文本的两段式，因为医疗场景对语音识别精度要求高（专业术语多），用专门的医疗 ASR（我们当时接的是阿里通义/讯飞）转文本后再喂给大模型。

这样语音质量问题被隔离在前置 ASR 节点，不影响主模型。

为什么不用端到端语音？

  • 端到端语音（Qwen2-Audio 类）2024 年还不是很成熟，医疗术语识别率低
  • ASR + 文本方案可解释性强——医疗器械备案时能清楚说"语音先转文本再进模型"
  • ASR 节点独立优化不影响主模型——比如换更好的医疗 ASR 模型不用重训

多模态融合的三路结构：

用户输入
  ├─ 文本（症状描述）→ Tokenize
  ├─ 图片（检查报告）→ ViT 编码
  └─ 语音（问诊录音）→ 医疗 ASR → 文本 → Tokenize
        ↓
  三路 Token 拼接 → Qwen2-VL Transformer → 推理输出

追问预案：
- "图片能看什么类型的检查报告？"→ "血常规、尿常规、心电图、CT 报告单，复杂影像如 MRI 由医生复核"
- "语音支持方言吗？"→ "支持普通话 + 粤语，沪语/川话识别率 70% 以下，建议用户用普通话"

第三部分：Prompt 与评估类问题

Q7：Prompt 怎么写的？（附完整示例）

参考回答：

我们的 Prompt 设计走的是"角色 + 知识边界 + 推理链 + 安全约束"四段式结构。以"预问诊追问 Prompt"为例：

# 角色
你是"善智星语"，一位在三甲医院有 20 年临床经验的全科医生，
擅长通过多轮问诊收集关键信息，为后续诊断提供结构化依据。

# 知识边界
- 可引用的知识：{知识图谱检索结果}，包含疾病标准、临床指南、药品知识
- 不可断言的内容：未在 {知识图谱检索结果} 中出现的疾病、药品、剂量

# 推理链
1. 先识别用户主诉的核心症状
2. 根据 {当前症状} 决定追问的优先级（危险症状 > 主症状 > 伴随症状）
3. 每次只问 1 个问题，保持自然问诊节奏
4. 累计 3-5 轮后输出结构化问诊小结

# 安全约束
- 不做最终诊断，仅提供"建议就诊科室"和"可能的鉴别方向"
- 出现以下关键词必须强制建议就医：胸痛、剧烈头痛、呕血、呼吸困难、意识障碍
- 涉及具体药品/剂量必须引用 {知识图谱检索结果}，否则回复"请咨询专业医生"

# 输出格式
{JSON 结构化字段}

调试过程中的关键经验：
1. 角色设定要给具体人设（"20 年三甲全科医生"比"医疗助手"好太多）
2. 知识边界必须显式声明——这是防幻觉的核心
3. 推理链用 CoT——让模型"先想后说"，复杂医学问题准确率能提 15-20%
4. 安全约束要硬编码——关键词触发强制就医建议，这个是 PM 主导设计的
5. 输出格式要结构化——下游接病历自动结构化模块，Prompt 里直接给 JSON schema

这个示例设计原则：
- 不写"我是 AI"套话——角色要落到具体人设
- 不写"请遵守医学伦理"空话——要落到具体关键词触发的具体动作
- 不给具体数字承诺（如"准确率 95%"）——避免被追问验证

Q8：怎么解决幻觉问题？

参考回答：

三道防线：

1. Prompt 层：强制要求模型引用 {知识图谱检索结果}，无引用不回答
2. RAG 层：所有医学结论必须先检索后生成，检索不到就明确告知"知识库暂无相关信息"
3. 后处理层：医疗高风险回答（诊断、用药、剂量）必须经过"安全关键词 + 规则引擎"二次校验

测评下来，幻觉率从初版的 18% 压到 5% 以下。

追问预案：
- "幻觉率怎么测的？"→ "随机抽 200 条模型回答，医生逐条核查医学事实是否正确"
- "5% 还能再降吗？"→ "技术上能，但成本不划算，剩余 5% 用人工二次确认兜底"
- "如果用户问到知识库没有的病怎么办？"→ "明确告知'知识库暂无相关信息，建议咨询专业医生'，绝不编造"

Q9：评估指标怎么设计的？

参考回答：

三个核心指标：
- 准确率：医生盲评 100 分制，≥ 80 分算通过
- 幻觉率：关键医学事实是否有事实依据，随机抽 200 条人工核查
- 响应时长：P95 < 3s（云端）/ < 8s（私有化 7B 部署）

不只看单次指标，更看纵向趋势——每周环比，主要看 Badcase 是不是新增的、还是历史问题的反复。

指标体系表格：

指标 目标 测量方式 频次
准确率 ≥ 80% 医生盲评 100 分制 每周
幻觉率 < 5% 抽 200 条人工核查 每周
响应时长 P95 < 1.8s（7B 量化） 埋点统计 实时
医生采纳率 > 70% 医生是否采纳模型建议 每日
用户满意度 NPS > 50 评分 + 文本反馈 每次会话

第四部分：合规与数据类问题

Q10：你们数据怎么脱敏的？（医疗数据合规全流程）

参考回答：

医疗数据合规是项目里PM 和法务联合主导的核心工作，分四层防护：

🔹 第一层：数据采集脱敏（输入端）

  • 患者姓名：替换为"患者 + 8 位哈希 ID"（不可逆）
  • 身份证号：保留前 6 位地区码 + 后 4 位，中间 8 位打码
  • 手机号：保留前 3 位 + 后 4 位，中间 4 位打码
  • 住址：只保留到"区/县"级
  • 就诊时间：保留"年-月"精度，去掉"日"

🔹 第二层：数据传输加密（管道端）

  • 传输层：TLS 1.3 全程加密
  • 存储层：AES-256 静态加密
  • 密钥管理：通过 KMS（密钥管理服务）托管，PM 无权接触明文密钥
  • 网络隔离：医疗数据专网，不与办公网互通

🔹 第三层：数据使用权限（访问端）

  • 最小权限原则：算法工程师只能访问自己训练任务的数据集
  • 数据脱敏后再训练：训练数据中所有可识别个人信息的字段全部替换
  • 操作审计：所有数据访问行为记录日志，保留 180 天
  • 双重审批：导出任何医疗数据需要 PM + 法务双重审批

🔹 第四层：数据销毁（生命周期）

  • 训练完的数据集：90 天后自动销毁
  • 客户私有化部署的数据：客户自主管理，我方不留副本
  • 模型权重中的隐私：通过 DP（差分隐私）训练，降低反演攻击风险

法规依据：

  • 《数据安全法》
  • 《个人信息保护法》
  • 《医疗机构病历管理规定》
  • 《GB/T 35273-2020 个人信息安全规范》
  • 等保三级（部分客户要求三级甲）

口径关键点：
- PM 主导的是流程 + 审批 + 审计——不是技术实现
- 强调"四层防护"——比说"我们数据脱敏了"更可信
- 主动提法规名——面试官会觉得你懂合规

追问预案：
- "差分隐私具体怎么做的？"→ "在梯度上加噪声，ε 控制在 3 以内，超过会导致模型精度掉点"
- "如果发生数据泄露怎么办？"→ "24 小时内上报网信办 + 通知用户 + 启动应急响应预案"
- "客户私有化部署的数据你们能看到吗？"→ "看不到，部署包只含模型权重，不含任何训练数据"

Q11：等保三级怎么过的？

参考回答：

等保三级是政企客户的硬门槛，我们当时分了五个域整改：

域 关键措施
安全通信网络 全站 HTTPS、WAF、流量清洗
安全区域边界 DMZ 区隔离、API 网关、IP 白名单
安全计算环境 主机入侵检测、数据库审计、漏洞扫描
安全管理中心 集中日志平台（ELK）、SOC 安全运营中心
安全管理制度 PM + 法务联合制定、年度评审、应急演练

PM 在其中的角色：
- 牵头安全管理制度编写（30+ 份文档）
- 协调第三方测评机构进场（一般 2-3 个月）
- 跟进整改项落地（测评后会有整改要求）
- 维护年度复测节奏（等保三级每年复测一次）

口径关键点：
- PM 不写技术整改方案——PM 负责管理制度的文档化和流程化
- 强调"30+ 份文档"——等保三级的合规文档量级
- 提"第三方测评"——显得你走过完整流程

第五部分：工程化与国产化类问题

Q12：国产化适配怎么做的？（信创 / 昇腾 / 海光）

参考回答：

医疗 B 端客户（尤其区县级卫健委、国资体检中心）必须走信创，这是硬门槛。我们当时做了两套国产化方案：

🔹 方案 A：华为昇腾 910B（主力方案）

  • 硬件：昇腾 910B 64G（4 卡或 8 卡）
  • 软件栈：CANN 7.0 + MindSpore + torch_npu
  • 模型迁移：从 NVIDIA CUDA 迁移到 CANN，主要工作是算子适配和性能调优
  • 精度损失：FP16 → FP16，精度损失 < 0.5%
  • 性能差距：相比 A100 80G，推理速度慢 15-20%（通过量化 + 算子优化补偿）

🔹 方案 B：海光 DCU / 寒武纪 MLU（备选方案）

  • 海光 DCU Z100：兼容 ROCm 生态，PyTorch 迁移成本低
  • 寒武纪 MLU370：用寒武纪自己的 BangC 算子库，迁移成本高
  • 选型原则：哪家更贴近客户已有 IT 栈就用哪家

适配过程中的坑：

  1. 算子缺失：Qwen2-VL 的某些自定义算子（动态分辨率切分）在昇腾上没现成实现，要自己写 CANN 算子
  2. 精度对齐：FP16 在某些算子上和 NVIDIA 结果有 1-2% 差距，需要逐层对齐
  3. 性能调优：昇腾的图编译（Ascend Graph Engine）调优需要重写部分算子融合逻辑
  4. 驱动版本：不同客户现场的驱动版本差异大，需要做兼容性测试矩阵

PM 在国产化适配中的角色：

  • 不是写代码——算法工程师负责算子迁移
  • PM 负责：
  • 客户需求调研（客户已有的 IT 栈、芯片采购清单）
  • 选型决策（昇腾 vs 海光 vs 寒武纪）
  • 项目排期（迁移周期 2-3 个月）
  • 客户验收（精度 + 性能 + 稳定性）

为什么必须做国产化？

  1. 政策强制：卫健委、医保局、医院的信息化项目 100% 要求信创
  2. 客户画像：区县级卫健委、地方医院大多是国资背景，采购清单限定国产芯片
  3. 数据出境管控：医疗数据不能出境，必须跑在国产芯片上
  4. 长期成本：NVIDIA 芯片供应链不稳定，国产芯片有国家补贴

口径关键点：
- PM 主导的是选型 + 排期 + 客户对接——不是写算子
- 强调"客户已有 IT 栈"——信创不是"用最好的是哪个"，而是"客户有什么就适配什么"
- 主动提华为/海光/寒武纪三个名字——显得真做过
- 主动提"算子缺失"等具体坑——避免被追问"具体怎么迁移的"

追问预案：
- "昇腾 910B 一张卡多少钱？"→ "商用 8 万左右，4 卡服务器整机 50-60 万"
- "为什么不选寒武纪？"→ "生态成熟度低，BangC 算子库覆盖不全，迁移成本高"
- "客户不接受国产化怎么办？"→ "这种情况基本不存在——信创是采购硬门槛，不接受就丢标"

第六部分：项目复盘类问题

Q13：怎么和院士团队合作的？PM 在其中起什么作用？

参考回答：

PM 在这个项目里其实是"医学专家与算法工程师的翻译官"：

  • 前期：把院士团队的医学标准翻译成"机器可理解的标注规范"
  • 中期：组织院士团队做 SFT 数据的标注质量审核，每批数据上线前都要过院士审
  • 后期：把模型输出的 Badcase 翻译成"算法工程师能理解的优化方向"

这个项目最深的体会是：医疗 AI 的 PM 必须懂医学基本逻辑——不需要会看病，但要懂"为什么医生要这样问诊""诊断依据是什么"。

具体动作：

  • 每月一次院士碰头会：汇报模型进展、收集医学反馈
  • 每周一次医生评测小组：拉 50 个真实病例盲评
  • 每日 Badcase 同步：医生发现的错误 24 小时内同步给算法工程师

Q14：模型部署在哪？推理成本怎么控？

参考回答：

两条线：

云端 API 模式：用 Qwen2.5-VL-72B 高精度版本，给 B 端高净值客户用，按 token 计费
私有化部署模式：7B 模型 + 量化（GPTQ/INT4）跑在客户自己的服务器上，一次性授权 + 年费

推理成本主要靠量化 + 缓存 + 检索增强压下来——高频医学问题走缓存，复杂问题才走全量推理。

成本明细表：

项目 7B 方案 14B 方案 72B 方案
训练算力 8×A100 × 1周 = ¥5万 8×A100 × 2周 = ¥10万 32×A100 × 4周 = ¥80万
推理硬件 1×A100 80G = ¥20万 2×A100 80G = ¥40万 8×A100 80G = ¥160万
电费/年 ¥0.5万 ¥1万 ¥4万
客户售价 一次性 ¥30万 + 年费 一次性 ¥50万 + 年费 API 按 token ¥0.1/千
毛利率 70% 60% 30%

结论：7B 方案毛利率最高、部署最广、迭代最快——这是 90% 医疗 B 端 AI 公司的共同选择。

Q15：你在这个项目里最难的决策是什么？

参考回答：

"模型能力边界"决策——什么病模型能看、什么病必须转人工。

我们设了三条红线：
1. 急症不接（关键词触发强制就医）
2. 罕见病不接（知识图谱覆盖度不够）
3. 儿童/孕妇/老人特殊人群不接（安全风险高）

这三条红线让我和医学团队吵了两个月——医生觉得"我能看为什么模型不能看"，我坚持"宁可漏诊不能误诊"。最后医学总监拍板支持了我这个保守策略。

这个决策直接影响了产品的商业定位——我们最终定位是"预问诊 + 健康咨询"，不是"在线问诊"。

为什么说这个决策难？

  1. 商业损失：砍掉 30% 的潜在用户（特殊人群是高 ARPU 用户）
  2. 团队分歧：医学团队不理解为什么不让模型"试试看"
  3. 合规风险：如果出事故，PM 是第一责任人
  4. 长期价值：保守策略反而让产品口碑更好，上线后零医疗事故

口径关键点：
- 这个故事体现 PM 的商业 + 合规 + 用户体验三维平衡能力
- "宁漏勿误"是医疗 AI 的金科玉律
- 强调"零医疗事故"——可量化的成果

❌ 不要说的（触发即减分）

雷区 替代说法
"我们是自研的 XX 亿参数大模型" "基于开源基座（Qwen2-VL）微调的垂直模型"

"我是项目负责人" "我主导产品设计和评测体系，算法负责人是 X"
"我们做了 100 万条数据" "院士团队 6 套标准 + 12 万条脱敏问诊对话 + 临床指南"

✅ 要强调的（加分项）

  1. PM 视角的主导动作：评测体系、Prompt 策略、Badcase 分析、需求边界
  2. 算法工程师的边界：负责训练实现和模型调优
  3. 院士团队的边界：负责医学专业度审核和数据标注
  4. 核心贡献量化：从 60 分做到 85 分，而不是从 0 到 1
  5. 商业价值：30+ 体检中心客户、多项荣誉、零医疗事故
  6. 合规意识：等保三级、信创适配、数据脱敏、医疗器械备案
